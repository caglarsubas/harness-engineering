# Bounded development-CI capacity exception — MET-RUNNER-001

Status: source-only proposal on accepted meta baseline `945de93f89c94f42f1d63bff7997e3d0fa704fc4`. This document is not a VM order, runner registration, installed trust bundle, successful CI check, or native Linux qualification. The historical [Linux readiness publication](LINUX_READINESS.md) remains byte-identical; this later, narrower exception changes only development-CI host acquisition, not its product gates.

## Scope and non-scope

One independently authorized, disposable Linux AMD64 self-hosted guest may serve one exact Harness-Onion pull-request verification job. The guest is external development infrastructure. The platform, tenant workflows, provider integrations, releases, live campaigns, and production deployments retain the zero-bill, no-paid-API and no-cloud-provisioning defaults. Public-cloud compatibility does not create an entitlement to provision tenant infrastructure. The repository contains no GCP provisioning command or credentials, and this packet changes no GitHub workflow.

No operator may register a listener from this source publication alone. Required independent operator records are a reviewed image and runner/toolchain/cache inventory; current signed root-owned launcher and preflight; exact-job admission authority; cost and egress approval; teardown controls; and a clean guest. A missing item is `NOT_RUN_ENV_UNAVAILABLE`, not a CI or native PASS.

## Bounded operator capacity

Before creation, the external operator must retain an immutable, independently approved record naming the GCP project, region/zone, image digest, machine type, disk and IP plan, one intended run, owner, creation/termination deadline, and numeric **all-in maximum authorized exposure**. A conservative worst-case preflight estimate must be below that limit using current prices and account state. It includes compute, boot and attached disk retention, IP, maximum permitted network egress, runner-control traffic, logs, monitoring, API/control-plane operations, and the independent watchdog and its storage or scheduler. The plan must bound each expected charge source through fixed termination, independently retried deletion and subsequent verification, including failure-path cleanup; free-tier assumptions are not a bound. This is an admission limit and operating plan, not a provider-enforced billing cap or guarantee against control-plane failure. A billing budget or alert is warning telemetry, **not** a hard spend cap. If egress or another expected charge source cannot be bounded, or the estimate exceeds the owner-approved limit, do not create or register the guest; failure to verify deletion must escalate immediately while the reservation remains open.

The guest must have no service account or metadata token, provider/API key, SSH agent, kubeconfig, Docker/containerd/Podman socket, inherited credential directory, shared host mount or billable broker. No warm-source checkout or snapshot may be mounted. The selected runner binary and pinned checkout action are immutable; runner auto-update is disabled. Pre-launcher egress permits only the reviewed GitHub runner-control and pinned-checkout destinations, subject to an external byte/rate ceiling and retained use counters. Repository acceptance itself remains deny-all outbound inside the signed launcher. A broad Internet rule, unrestricted egress, mutable package fetch or automatic image pull blocks registration.

The runner still needs one-job registration/session material; `credential-free` means there are no **ambient cloud or billable capabilities**, not that GitHub session files do not exist. Keep runner home and `.credentials`, runner `_temp` event files, process/proc handles and token-bearing paths outside the checkout and hidden from the isolated repository process. Checkout must keep `persist-credentials: false`; the launcher supplies a closed child environment. Neither the hook nor launcher may log event payloads, registration data, signed authority secrets or tokens.

The unchanged `offline-readiness` workflow has a 15-minute `verify` job limit. Before registration, retain representative target-host throughput evidence that the complete declared command set plus admission, checkout, launcher and cleanup fits that limit with margin on the proposed guest. The accepted macOS timing is not Linux proof; a smaller Linux machine may miss the bound. If this cannot be established, keep CI queued or report `NOT_RUN_ENV_UNAVAILABLE`. This packet cannot extend the workflow timeout, omit commands or bypass acceptance to accommodate a slow host.

Only one ephemeral/JIT runner is registered for a single job, after a fresh queue and repository check. GitHub labels are routing hints, not a cryptographic job binding. At this source checkpoint, [PR #141](https://github.com/caglarsubas/harness-onion/pull/141) and [draft PR #142](https://github.com/caglarsubas/harness-onion/pull/142) both have queued `verify` checks on the same labels. The operator must serialize them and establish which exact job is eligible before registering a listener; this packet authorizes no cancellation or rerun. An unexpected assignment still fails closed and consumes that job attempt. Never weaken the signed admission to rescue it. One fixed termination timestamp and an automatic guest delete action are mandatory; a separate watchdog with independent custody and independently budgeted control-plane access must delete the VM and any attached disk/IP even if the runner crashes or loses GitHub connectivity. Verify exit, deregistration, VM/disk/IP deletion and retained usage counters; perform a later billing reconciliation. Until all cleanup observations exist, the reservation remains active and no completion is claimed.

## Sole pre-checkout admission exception

The only code allowed before GitHub's pinned credential-free checkout is the externally installed root-owned, nonwritable `ACTIONS_RUNNER_HOOK_JOB_STARTED` admission hook and its root-owned verifier. The runner invokes the hook under its unprivileged UID; a narrowly scoped, root-owned verifier/helper owns the immutable packet and durable nonce ledger through a fixed local IPC interface, with no shell, arbitrary command, broad sudo or writable trust path. It is not supplied by the checkout and has a hard independent timeout. [GitHub documents](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts) that this hook runs before job steps, fails the job on a nonzero exit, and has no built-in timeout. It reads a locally installed, independently signed and unexpired one-job admission record.

The admission trust anchor is an externally installed, root-owned public-key bundle whose exact SHA-256 digest is pinned in the reviewed guest-image/operator inventory, separate from the existing offline-launcher manifest key. Verification accepts only an operator-approved signature algorithm and key with the explicit purpose `DEVELOPMENT_CI_JOB_ADMISSION_V1` and domain `planeon/harness/development-ci-job-admission/v1`; generic release, tenant, campaign or packet signatures cannot satisfy it. The root-owned policy admits exactly one active signed record and one active admission key for this guest and job. A missing, writable, digest-mismatched, expired or revoked anchor or record fails closed. Revocation state is root-custodied, signed by the independent admission authority, valid for the whole proposed guest lifetime, and checked before nonce reservation. Rotation requires a new reviewed image/trust-bundle digest and new single-job authority before registration; no overlapping old/new key acceptance or in-place fallback is allowed. A compromised or revoked key retires the guest and its unused authority. The record binds:

- repository **ID and name**; same-repository `pull_request` event only, explicitly denying `workflow_dispatch` and forks by default;
- exact PR number, `refs/pull/<number>/merge`, head SHA, base SHA and synthetic merge SHA;
- workflow path and `GITHUB_WORKFLOW_SHA` checked against operator-approved workflow content digest; run ID, run attempt, GitHub's numeric job ID as independently observed by the controller, and the observed `GITHUB_JOB` context name as a separate field. The approved workflow digest must describe exactly one non-matrix `verify` job, so the signed run/attempt/workflow/job-context tuple identifies a single numeric job;
- expected packet ID/digest, runner binary/image identities, signing purpose, nonce, issue/expiry and fixed termination timestamp.

Before checkout, compare each observable runner/job field to the signed record, verify the packet digest against root-custodied local packet bytes, reject missing or extra authority, and atomically reserve the nonce in a root-owned, durable one-shot ledger. The external controller binds the numeric GitHub job ID to the unique run/attempt/workflow/job-context tuple before registration and signs that mapping; the hook verifies the tuple and runner identity, not an invented numeric-ID environment variable. [GitHub defines `GITHUB_JOB` as the workflow's string job key](https://docs.github.com/en/actions/reference/workflows-and-actions/variables), while its [workflow-jobs API](https://docs.github.com/en/rest/actions/workflow-jobs) has a separate numeric `id`. This indirect binding is valid only while the reviewed workflow has exactly one non-matrix job and the controller has freshly verified the numeric job's queued state, PR, runner scope and tuple; any workflow topology change requires new authority. Before registration, an operator must test the exact pinned runner build on a controlled Linux host and retain evidence that the pre-job hook receives and authenticates every required observable tuple field before checkout. A simulated environment variable, parsed event file, PR title/body, or post-checkout API call does not satisfy that test. If any field is unavailable or ambiguous, registration remains blocked pending a separately reviewed contract revision. Timeouts, duplicate nonce, changed merge ref, stale commit, unexpected run or incomplete comparison fail before any step. `GITHUB_EVENT_PATH` is untrusted data, never authority. The hook holds no cloud credential or broad GitHub token. The root-owned signer/controller obtains authoritative GitHub observations outside the guest and keeps registration credentials hidden from the job.

GitHub can still assign the wrong queued job because both PRs currently request the same labels. The hook must fail that assignment before checkout; queue sequencing is a distinct operator action, not a claim that runner labels guarantee the intended job. After the pinned checkout, the workflow's only repository-facing run step remains `/opt/planeon/bin/harness-offline-launch`. The launcher verifies its existing signed manifest, exact packet/commit, complete warm-root inventory and fresh Linux OS isolation before opening or executing any repository file. The hook does **not** replace launcher verification or turn source tests into native acceptance.
